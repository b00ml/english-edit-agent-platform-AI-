## 3. P0 详细设计

### P0-1 结构化输出校验错误回注重试

**问题**：G1。重试耗尽前模型反复犯同类错误，重试成功率低且成本翻倍。

**方案**（对齐 [Instructor 的 reask 模式](https://python.useinstructor.com/)，自行实现以保持对任意 OpenAI 兼容端点的通用性）：

1. 将单发调用改为**多轮消息列表**。首轮：`[system, user(经 json-enforce.st 包装)]`（不变）。
2. 校验失败时向消息列表追加两条：
   - `assistant`：上次原始输出（`json.dumps(ensure_ascii=False)`，截断 2000 字符）；
   - `user`：由新 prompt 文件 `prompts/retry-feedback.st` 渲染的错误反馈（错误摘要 + 修正指令）。
3. 错误摘要纯函数 `_summarize_validation_error(exc) -> str`：
   - `ValidationError` → 遍历 `exc.errors()`，每条输出 `字段路径 -> 错误类型: msg`（`loc` 用 `.` 连接，`input` 截断 80 字符），最多列 10 条；
   - `json.JSONDecodeError` → `"输出不是合法 JSON: {exc}"`；
   - `KeyError` → `"输出缺少预期字段: {exc}"`。
4. `STRUCTURED_RETRY_FEEDBACK=false` 时保持现状（原样重发），作为回滚开关。

```python
# structured_output.py 重试循环改造（示意）
messages = [{"role": "system", "content": system_prompt},
            {"role": "user", "content": final_user}]
for attempt in range(1, max_retry + 1):
    try:
        raw, latency_ms, usage = _call_openai_json(client, model_name, messages)
        validated = output_model.model_validate(_normalize_flat(schema, raw))
    except (ValidationError, json.JSONDecodeError) as exc:
        summary = _summarize_validation_error(exc)
        # 失败尝试也落 TraceLog（P0-2）。usage/latency 需在解析失败时同样可得：
        # _call_openai_json 应先从 resp.usage 提取再抛错（实施细节）
        record_trace(..., stage="generate", attempt=attempt, success=False,
                     output_data={"error_summary": summary}, latency_ms=latency_ms,
                     cost=compute_cost(usage, model_name))
        if attempt >= max_retry:
            break
        # 回注仅对 ValidationError 路径附带上次输出（raw 已解析）；
        # JSONDecodeError 无可用结构化输出，重试消息仅含错误说明
        if settings.STRUCTURED_RETRY_FEEDBACK and isinstance(exc, ValidationError):
            messages += [
                {"role": "assistant", "content": json.dumps(raw, ensure_ascii=False)[:2000]},
                {"role": "user", "content": render(load_prompt("retry-feedback.st"),
                        {"error_summary": summary})},
            ]
        continue
    record_trace(..., stage="generate", attempt=attempt, success=True,
                 latency_ms=latency_ms, cost=compute_cost(usage, model_name))
    return validated.model_dump()
```

**涉及文件**：`engine/structured_output.py`（改造）、`prompts/retry-feedback.st`（新增）、`config.py`（开关）、`tests/test_structured_output.py`（增测）。

**测试计划**：
1. mock 客户端首次返回嵌套包装、第二次返回合法 → 断言第二次请求的 `messages` 含错误摘要与上次输出；
2. 重试耗尽 → `StructuredOutputError` 消息含各次错误摘要；
3. 开关关闭 → 各次请求 messages 完全一致（回归保障）；
4. `_summarize_validation_error` 对嵌套 `loc`、超长 `input` 截断的格式断言。

**验收**：重试请求可观测到错误反馈注入；失败尝试全部落 TraceLog（联动 P0-2）。

### P0-3 Checkpointer 持久化（MemorySaver → PostgresSaver）

**问题**：G3。"断点续跑"语义在进程重启后失效。

**方案**（依据 [LangGraph 官方持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)）：

1. 依赖：`requirements.txt` 增加 `langgraph-checkpoint-postgres`（携带 psycopg3）。
2. `graph.py` 改造为惰性单例工厂，替换模块级 `_checkpointer = MemorySaver()`：

```python
_checkpointer: Optional[BaseCheckpointSaver] = None
_checkpointer_lock = threading.Lock()

def _get_checkpointer():
    global _checkpointer
    if _checkpointer is not None:
        return _checkpointer
    with _checkpointer_lock:
        if _checkpointer is not None:
            return _checkpointer
        if settings.CHECKPOINTER_BACKEND == "postgres":
            try:
                dsn = settings.DATABASE_URL.replace("+psycopg2", "")
                saver = PostgresSaver(psycopg.connect(dsn))
                saver.setup()   # 建表 + 迁移，幂等
                _checkpointer = saver
                return _checkpointer
            except Exception as exc:   # noqa: BLE001 —— 精确记录后降级
                logger.warning("PostgresSaver 初始化失败，降级 MemorySaver: %s", exc)
        _checkpointer = MemorySaver()
        return _checkpointer
```

3. `build_graph()` 改用 `_get_checkpointer()`；`setup()` 幂等，每个进程首个调用方执行一次（backend lifespan 与 worker 首个任务各自一次），无需额外挂载点。
4. **降级策略**：postgres 初始化失败 → 记 warning 后回退 MemorySaver（个人项目规模下可用性优先于纯度；日志可定位配置错误）。显式 `CHECKPOINTER_BACKEND=memory` 可强制旧行为。
5. **续跑语义修正**（这是本项的核心收益）：`thread_id = f"{task_id}:{idx}"` 已按条粒度稳定。配合 P0-6 的重新投递后，`graph.invoke` 对已完成的 thread 直接返回落库的最终状态（不重复生成），对中断的 thread 从最后 checkpoint 续跑 —— "中断后已完成条目不重复生成"从进程内局部真理变为跨重启保证。`run_generation` docstring 同步更新。
6. 容量治理（P2 备注）：PostgresSaver 自建 `checkpoints` 等表，行数随任务累积；后续可加周期清理任务删除 N 天前已完成任务的 checkpoint，本期不做。

**涉及文件**：`workflow/graph.py`、`config.py`、`requirements.txt`、`tests/test_validation.py`（后端选择逻辑增测）。

**测试计划**：
1. 单测：`CHECKPOINTER_BACKEND=memory` → 返回 MemorySaver；postgres 初始化抛错 → 降级 MemorySaver 且仅告警一次；
2. 集成测试（P1-4 框架下，标记 integration）：setup 建表 → 写入 checkpoint → 新连接读回一致。

**验收**：worker 中途 kill 后重新启动重跑同任务，已完成条目不重复调用 LLM（TraceLog 无重复 trace 段）。

### P0-4 Judge 一致性评估（accuracy + Cohen's kappa）

**问题**：G4/G5。"校准"没有一致性数字背书；行业共识是只报准确率不报 chance-corrected 一致率等于没校准（[arXiv 2406.12624](https://arxiv.org/html/2406.12624v1)）。

**方案**：

1. 新增纯函数模块 `app/engine/agreement.py`（零第三方依赖，手写 kappa 约 15 行，避免引入 sklearn）：

```python
def cohen_kappa(y_true: list, y_pred: list) -> float:
    """Cohen's kappa = (po - pe) / (1 - pe)；pe=0 时约定返回 1.0。"""
def judge_vs_manual(pairs: list[tuple[float, float]], threshold: float) -> dict:
    """pairs: (auto_total, manual_score)。judge 判定 auto>=threshold 为通过，
    真值 manual_score>0 为通过。返回 {confusion, accuracy, precision, recall, f1, kappa, n}。"""
```

2. 新增脚本 `scripts/judge_agreement.py`（对齐既有 `judge_stability.py` 的脚本风格）：
   - 从 DB 收集同 item 的 auto/manual 记录对（复用 `calibration.collect_labeled` 的查询逻辑，但保留全部配对而非仅 FP 集）；
   - 守卫：配对数 < `--min-samples`（默认 30）时输出"样本不足"报告，不硬算；
   - 参数：`--template` / `--threshold` / `--min-samples` / `--output-file`；
   - 只读分析，不写 DB；输出混淆矩阵 + 指标 + 按"auto 高分人工驳回"分层的 FP 明细（供校准分析复用）。
3. `POST /api/quality/calibrate` 响应体增加只读字段 `agreement`（调用同一纯函数），校准中心页可展示"本次校准样本集上 judge 与人工的一致率/kappa"。

**诚实边界（写进脚本输出与文档）**：人工记录仅有总分二值（通过/驳回），故一致率为**二值判定级**，不计算维度级加权 kappa；同族 judge 的自偏好由 P1-2 治理。报告明确标注口径，不夸大。

**涉及文件**：`engine/agreement.py`（新增）、`scripts/judge_agreement.py`（新增）、`api/routes.py`（calibrate 响应扩展）、`tests/`（新增 test_agreement.py）。

**测试计划**：kappa 与手算值对照（完全一致=1.0、给定混淆矩阵的固定值、pe≥1 边界）；judge_vs_manual 的 precision/recall 口径；守卫触发行为。

**验收**：跑一次脚本产出真实数字，该数字即简历"judge 与人工一致率 XX%、kappa X.X"的合法来源。

### P0-6 Celery 任务可靠性（acks_late + 有限重试 + 僵尸恢复）

**问题**：G7。worker 崩溃 → 任务永久卡 running；无重试语义。

**方案**：

1. **broker 可见性**：`broker_transport_options={"visibility_timeout": 3600}`（须大于硬超时 900s + 重试延迟之和，防未 ack 消息被提前重投）。
2. **任务投递语义**：`process_generation_task` 设置 `acks_late=True`、`task_reject_on_worker_lost=True` —— worker 崩溃时消息重投而非丢失。
3. **任务级重试**：`bind=True, max_retries=settings.TASK_MAX_RETRIES, autoretry_for=(redis.exceptions.ConnectionError, sqlalchemy.exc.OperationalError), retry_backoff=True, default_retry_delay=60`。仅对**瞬态基础设施错误**自动重试；业务异常（生成耗尽等）不重试，维持部分成功聚合语义。**重试幂等性由 P0-3 保证**（重投后已完成条目经 checkpoint 秒回，不重复调用 LLM），两项必须同批上线。
4. **僵尸任务恢复**：celery `worker_ready` 信号 → `recover_stale_tasks()`：`status='running' AND updated_at < now()-STALE_TASK_SECONDS` → 置回 `pending` 并重新入队（`updated_at` 已有 onupdate，无需迁移）。`GenerationTask.progress` 保留，重跑从断点继续。

```python
@celery_app.on_after_configure.connect  # 或 worker_ready 信号，实施时按 celery 版本择一
def setup_periodic(sender, **_): ...
# recover_stale_tasks 为纯函数式查询+置状态+enqueue，独立成模块便于单测
```

**涉及文件**：`worker/celery_app.py`、`worker/tasks.py`、`worker/recovery.py`（新增）、`config.py`、`tests/`（新增 test_worker_recovery.py）。

**测试计划**：`recover_stale_tasks` 对过期 running / 新鲜 running / 非 running 三类行的行为断言（enqueue 调用以 monkeypatch 验证）；任务属性断言（acks_late/max_retries/autoretry_for 已生效）。

**验收**：任务执行中 kill worker → redis 消息重投或僵尸恢复二途必居其一，任务最终态 ∈ {succeeded, partially_succeeded, failed}，不出现永久 running。

## 4. P1 详细设计

### P1-1 LangGraph interrupt 人工卡点（灰区转人工）

**问题**：G12。人工审核完全在图外，无 human-in-the-loop；灰区内容（分数接近阈值）要么侥幸入库要么白白熔断。

**方案**：

1. **灰区路由**：模板 `run_config.human_review = {enabled, gray_margin}`（默认关闭，零行为变化）。`after_qc` 路由升级为三段：
   - `score >= threshold` → `store`（不变）；
   - `enabled && score >= threshold - gray_margin` → `human_review`（灰区优先转人工，**不消耗改版预算**）；
   - 其余 → `revise` / `reject`（不变）。
2. **human_review 节点**（两段式，注意 interrupt 重执行陷阱）：

```python
def human_review_node(state, session):
    # 段一（幂等）：interrupt 恢复后节点会从头重执行，必须以 content_id 判断跳过已做副作用
    if not state.get("content_id"):
        item = store_draft(state, status="awaiting_review")   # 落库草稿 + auto 质检记录 + 站内通知
        return {"content_id": item.id, "status": "awaiting_review"}  # 触发检查点保存
    decision = interrupt({"qc_score": state["qc_score"],
                          "dimension_scores": state["dimension_scores"]})
    # 段二：拿到人工裁决后收尾
    apply_review_decision(session, state["content_id"], decision)  # 更新状态 + 写 manual 记录
    return {"status": "review_passed" if decision["approved"] else "review_rejected"}
```

   路由：`human_review → END`（通过/驳回均为终态，裁决权在人）。
3. **恢复入口**：`workflow/graph.py` 新增 `resume_human_review(thread_id, decision, session)`，以 `Command(resume=decision)` 续跑。`review_content` API（`routes.py:350`）改造：`item.thread_id 非空且 status=='awaiting_review'` → 走恢复路径；否则走现有路径（老数据完全兼容）。
4. **数据迁移**：`content_item` 增列 `thread_id VARCHAR(128) NULL`（§6）；状态枚举增加 `awaiting_review`。
5. 前端 `QualityPage` 增 `awaiting_review` 筛选（可选项，后端先行）。

**涉及文件**：`workflow/graph.py`、`api/routes.py`、`models.py`、`schemas.py`、`notification.py`、迁移、`tests/test_validation.py`。

**测试计划**（状态机级，fake LLM 节点）：灰区 → 结果含 `__interrupt__` 且草稿落库 awaiting_review；`Command(resume={"approved": True})` → 终态 passed 且 manual 记录正确；resume 驳回 → rejected；`enabled=false` / 高分 / 低分路径与现状完全一致（回归）。

**验收**：灰区题目出现在人工队列，裁决后终态正确，全程无需重启进程（PostgresSaver 跨进程恢复）。

### P1-2 Judge 独立模型配置（自偏好偏差治理）

**问题**：G10。judge 与生成模型同源时存在自偏好偏差（[行业共识：judge 应与被评模型不同族](https://futureagi.com/blog/llm-as-judge-best-practices-2026/)）。

**方案**：全局 `JUDGE_MODEL_NAME`（空=沿用 `LLM_MODEL_NAME`，完全向后兼容）+ 模板级 `run_config.judge_model` 覆盖（优先级：模板 > 全局）。`quality.py` 与 `graph.py::qc_node` 按此顺序解析。运营口径写入模板注释：**judge 应配置为与生成主模型不同家族的模型**。TraceLog 按 model+stage 已可拆分 judge 成本，无需改造。

**测试**：三层解析优先级单测；默认值回归（不配置时行为与现状一致）。

### P1-3 分模型价目表

**问题**：G9。

**方案**：`MODEL_PRICES: dict = {}`（env 传 JSON，pydantic-settings 原生支持），键为模型名，值为 `{"prompt": 元/1K, "completion": 元/1K}`。`trace.py::compute_cost / token_breakdown` 改为：命中价目表 → 按输入/输出分别计价；未命中 → 回退 `COST_PER_1K_TOKENS`（历史行不动，口径平滑过渡）。`ModelProfile` 表不加价格列（价格变动频率高，配置层比数据层合适，此取舍记录在案）。

**测试**：命中/未命中/缺 completion 单价回退三分支；两模型不同单价的成本 disaggregation 断言。

### P1-4 集成测试层 + CI

**问题**：G11。模型使用 pgvector `Vector(1024)` 与 JSONB，**sqlite 内存库不可行**，集成测试必须真 Postgres。

**方案**：

1. **可测性前置重构**：`structured_output.py` / `quality.py` 中内联 `OpenAI(...)` 构造提取为模块级 `_get_openai_client()`（行为不变，仅为 monkeypatch 提供缝）。
2. **集成测试** `tests/integration/`（pytest marker `integration`，默认跳过，需 `TEST_DATABASE_URL`）：
   - 端到端：登录 → 创建任务（mock LLM 客户端）→ 轮询至终态 → ContentItem + QualityRecord + TraceLog 三表断言；
   - 状态机全图：通过 / 改版 / 熔断三路径；
   - checkpointer 持久化 round-trip（联动 P0-3）；
   - 去重 409。
3. **CI**（`.github/workflows/backend-ci.yml`）：services 用 `pgvector/pgvector:pg16` + `redis:7`；两个 job——单测（`pytest -m "not integration" --cov=app --cov-fail-under=80`）与集成（带 `TEST_DATABASE_URL`）。覆盖率门槛 80% 与 PRD 成功指标对齐，**CI 输出即"覆盖率 X%"数字来源**。`requirements-dev.txt` 增 `pytest-cov`。

**测试**：CI 首跑绿即验收。

## 7. 指标口径定义（数字字典 —— 简历数字的唯一合法来源）

| 指标 | 计算口径 | 数据来源 | 用途 |
|------|----------|----------|------|
| 结构化首过率 | `success=TRUE 且 attempt=1 的 generate 行 / success=TRUE 的 generate 行` | trace_log | 简历"结构化符合率" |
| 平均尝试次数 | `avg(attempt) over success=TRUE 的 generate 行` | trace_log | 重试成本叙述 |
| 结构化最终失败率 | `无 success 行的 trace_id 数 / 去重 trace_id 总数`（thread 级） | trace_log | 结构化输出可靠性 |
| judge-人工一致率 / kappa | P0-4 脚本输出，`n≥30` 才报告 | quality_record(auto/manual 配对) | 简历"一致率 XX%、kappa X.X" |
| 人工驳回率 | `manual_review score=0 / (pass + reject)`（现状沿用） | quality_record | 质量闭环效果 |
| 改版触发率 | `revise_count>=1 的入库条目 / 入库条目总数` | content_item | 自动改版触发率 |
| 单题生成成本 | `SUM(trace_log.cost) / 入库条目总数`（或按任务下钻） | trace_log | 简历"单题成本" |
| 单测覆盖率 | CI `--cov` 输出，门槛 80% | CI | 简历"覆盖率" |

> 纪律：**先有口径与数字，再改简历**。任一指标无实测数字前，简历对应位置留白，不写占位值。

## 8. 风险与回滚

| 风险 | 缓解 | 回滚 |
|------|------|------|
| PostgresSaver 连接占用 / 线程安全 | v1 单连接（LangGraph 内置锁串行化检查点写），批量瓶颈出现再升级连接池 | `CHECKPOINTER_BACKEND=memory`（代码自动降级已内置） |
| 失败尝试写 TraceLog 放大写入量 | 上限受 max_retry=3 约束，量级可忽略 | 停写失败行（P0-1 开关关闭不影响成功行写入） |
| acks_late + 重投导致重复生成 | 依赖 P0-3 thread 级幂等，**两项同批上线**为硬约束 | 任务级 autoretry 关闭，acks_late 可独立保留 |
| interrupt 重执行副作用 | 段一以 `content_id` 幂等守卫（设计已内置） | 模板 `human_review.enabled=false` 即回旧行为 |
| 分发 Sink 引入网络故障面 | 各 sink 独立捕获、失败互不影响（沿用现有约定） | `TRACE_SINKS=db` |
| 指标口径与历史数据不一致 | 全部新指标基于新列（默认值对历史行解释为 attempt=1/success=TRUE） | 不适用（只增不改） |
