# 优化技术设计 3.0 —— 生产一致性、安全边界与可运维性加固

> **文档状态**：设计稿，待实施
>
> **编制日期**：2026-09-07
>
> **适用版本**：英语教研 AI 内容生成平台 2.0（下一阶段优化）
>
> **目标**：将当前已经串通的“选题 → 生成 → 校验 → 质检 → 改版 → 入库 → 人工审核 → 发布”链路，收敛为可恢复、可隔离、可审计、可运维的生产系统。
>
> **重要边界**：本文是优化设计，不代表代码已经实现。除“现状证据”章节外，所有方案、接口、迁移和指标均属于待实施内容。

---

## 1. 设计结论

当前项目没有方向性错误。LangGraph + FastAPI + Celery + PostgreSQL/pgvector 的技术路线与“配置驱动的 AI 内容生产线”定位一致；现阶段真正的问题是生产一致性没有闭环：流程状态、数据库事务、消息投递、权限边界和租户字段各自存在，但没有形成一套强制约束。

必须直接指出：当前系统不能把“可恢复”“多租户预留”“发布管控”“任务可靠投递”当作已完成能力。源码证据表明，这些能力仍有绕过路径。3.0 不新增题型、不扩展前端功能面，优先修复状态和边界，再做拆分与优化。

### 1.1 最高优先级

| 优先级 | 目标 | 必须解决的事实问题 | 交付判断 |
|---|---|---|---|
| P0-1 | 终态一致性 | `reject_node()` 不落库；worker 将非 interrupt 结果一律计为 succeeded；发布接口不检查当前状态 | 任一条目和任务都能解释最终结果，拒绝/失败不会伪装成成功 |
| P0-2 | 租户与权限隔离 | `tenant_id` 可由客户端传入，查询普遍没有 tenant filter；viewer 能读取未发布内容 | 用户只能看到和操作其租户、其角色允许的数据 |
| P0-3 | 投递与幂等一致性 | 数据库提交和 `send_task()` 分离；`request_hash` 只有普通索引，竞态下仍会重复任务 | 任务创建、投递、重试、死信均可追踪，重复提交不会制造重复执行 |
| P0-4 | 生产安全基线 | JWT、管理员、数据库和 Langfuse 默认密钥可直接启动 | 生产配置缺失时 fail-fast，敏感默认值不再可用 |

### 1.2 本期非目标

- 不迁移到 Temporal。Temporal 的事件溯源、History Service、Task Queue 和 DLQ 值得借鉴，但对当前个人可维护项目过重。
- 不重写 LangGraph。保留现有状态图，先修复状态契约和副作用边界。
- 不把所有 API 一次性拆成微服务。先做模块内 `service/repository` 分层，保持单体部署。
- 不在本期做模型微调、复杂多模态、跨区域容灾和计费系统。
- 不用 Prompt 代替权限、数据隔离、结构化校验或审计。

### 2.1 当前可靠性判断

| 能力 | 当前真实水平 | 不能使用的表述 |
|---|---|---|
| LangGraph 断点 | PostgresSaver 正常时可跨进程；初始化失败会降级 MemorySaver | “任何生产故障都可可靠续跑” |
| Celery 投递 | 有 `acks_late`、瞬态异常重试和僵尸恢复，但创建与投递不是同一事务 | “任务必达” |
| 多租户 | 数据模型有预留字段 | “已实现多租户隔离” |
| 人工审核 | 灰区路径使用 interrupt；普通内容仍可由 API 直接改状态 | “所有发布都经过审核” |
| 可观测 | TraceLog 能记录主要 LLM 调用 | “全链路包括 embedding、队列、数据库健康均可观测” |

## 3. 目标架构

### 3.1 目标分层

```text
React 工作台
    │ REST / OpenAPI
    ▼
FastAPI API（认证、TenantContext、Pydantic 入参、统一错误）
    │
    ▼
Application Service（生成、审核、发布、知识库、通知）
    │                 │
    ▼                 ▼
Repository（强制 tenant scope）  Outbox（同事务写入）
    │                 │
    ▼                 ▼
PostgreSQL / pgvector        Outbox Relay → Redis/Celery
                                  │
                                  ▼
                         Celery item worker / DLQ
                                  │
                                  ▼
                     LangGraph + PostgresSaver
                       │       │       │
                       ▼       ▼       ▼
                    engine    rag    Trace sinks
```

### 3.2 设计原则

1. **状态以数据库终态为准**：图状态是执行过程，任务和内容表是对外事实源；任何终态都必须有持久化记录。
2. **副作用只能落在可重试边界内**：数据库写入必须幂等；消息发送必须通过 Outbox；节点在 interrupt 前不得产生不可重复副作用。
3. **租户来自认证上下文**：请求体不得决定数据归属；所有 Repository 默认需要 `TenantContext`。
4. **发布是状态迁移，不是字段赋值**：只能从允许的前置状态进入 `published`，并记录操作者和时间。
5. **可选依赖失败必须显式可见**：RAG、Langfuse、PostgresSaver 可以配置降级，但必须有健康状态、日志和告警；生产默认不允许静默降级。
6. **配置驱动只解决业务变化，不掩盖契约缺失**：题型规则仍放 YAML/Schema，权限、状态、错误码和事务语义由代码强制。

## 4. 状态与接口契约

### 4.1 任务状态

将任务状态集中到 `backend/app/domain/status.py`，禁止在 API、worker、workflow 中继续散落字符串。

```text
pending
  └─ dispatched
       └─ running
            ├─ awaiting_review
            ├─ succeeded
            ├─ partially_succeeded
            ├─ failed
            └─ cancelled
```

说明：

- `dispatched` 表示 Outbox 已成功交给 broker，避免 `pending` 同时表示“未投递”和“等待执行”。
- `awaiting_review` 表示仍有条目等待人工裁决，不得向调用方返回成功。
- `partially_succeeded` 只表示同时存在成功和失败/拒绝条目；只有所有条目完成且无失败、无待审核时才是 `succeeded`。
- `cancelled` 只能由显式取消 API 或运维操作产生，不能用异常字符串代替。

### 4.2 内容状态

```text
generated → pending_qc → passed → published
                    ├── rejected
                    └── awaiting_review → passed / rejected
```

允许迁移：

| 当前 | 目标 | 触发方 |
|---|---|---|
| `pending_qc` | `passed` / `rejected` / `awaiting_review` | workflow / 人工审核 |
| `awaiting_review` | `passed` / `rejected` | `quality:review` |
| `passed` | `published` | `content:publish` |
| `published` | 任何状态 | 禁止，除非新增显式下线流程 |
| `rejected` | `published` | 禁止 |

`publish_content()` 必须使用条件更新或数据库锁：

```sql
UPDATE content_item
SET status = 'published', published_by = :user_id, published_at = now()
WHERE id = :content_id AND tenant_id = :tenant_id AND status = 'passed';
```

更新行数为 0 时返回 `CONTENT_STATE_CONFLICT`，不能把任意状态强制改为发布。

### 4.3 统一结果契约

`run_generation()` 和 item worker 统一返回：

```json
{
  "item_status": "stored|awaiting_review|rejected|failed|cancelled",
  "content_id": "uuid|null",
  "failure_code": "string|null",
  "failure_reason": "string|null",
  "trace_id": "string",
  "retryable": false
}
```

worker 只能依据 `item_status` 统计，不得使用“不是 interrupt 就成功”的反向推断。

### 4.4 错误码

统一响应形态：

```json
{
  "code": "CONTENT_STATE_CONFLICT",
  "detail": "内容当前状态为 rejected，不允许发布",
  "request_id": "uuid"
}
```

最低错误码集合：

| 错误码 | HTTP | 场景 |
|---|---:|---|
| `AUTH_REQUIRED` | 401 | 未登录或 token 无效 |
| `TENANT_SCOPE_DENIED` | 403 | 资源不属于当前租户 |
| `PERMISSION_DENIED` | 403 | 角色没有操作权限 |
| `TEMPLATE_NOT_FOUND` | 404 | 模板不存在或不可用 |
| `CONTENT_NOT_FOUND` | 404 | 内容不存在或不可见 |
| `CONTENT_STATE_CONFLICT` | 409 | 状态迁移不合法 |
| `DUPLICATE_TASK` | 409 | 活跃任务幂等冲突 |
| `INVALID_TEMPLATE_PARAMS` | 422 | 不符合 input schema |
| `TASK_NOT_CANCELABLE` | 409 | 任务已进入不可取消阶段 |
| `DEPENDENCY_UNAVAILABLE` | 503 | DB、Redis 或 checkpointer 不可用 |

## 5. P0 详细设计

### P0-1 状态机终态与任务统计闭环

#### 目标

让每个条目都有可解释的终态，让任务汇总与条目事实一致，禁止成功统计依赖隐式返回值。

#### 改动

1. 新增 `backend/app/domain/status.py`：集中定义任务、内容和 item result 状态以及合法迁移表。
2. 改造 `backend/app/workflow/graph.py`：
   - `reject_node()` 创建 `ContentItem(status="rejected")`，绑定自动 `QualityRecord`、`failure_code=QUALITY_THRESHOLD_NOT_MET` 和拒绝原因。
   - `store_node()` 明确返回 `item_status="stored"`（内容表状态为 `pending_qc`），不再让调用方猜测。
   - 所有节点异常转换为结构化 `WorkflowFailure`，由 worker 记录到任务失败明细。
   - `ContentItem` 增加 `failure_code`、`failure_reason`、`published_by`、`published_at`；审计敏感字段不放在 JSONB payload 中。
3. 改造 `backend/app/worker/tasks.py`：
   - 使用结果契约统计 `succeeded/rejected/failed/awaiting`。
   - 每条 item 的结果写入 `generation_task_item`（推荐）或至少写入 `GenerationTask.result_summary`，不能只保留前 5 条异常字符串。
   - 任务终态由数据库聚合计算，禁止仅用本次 Python 循环计数覆盖其他 worker 的结果。
4. 改造 `backend/app/notification.py`：通知使用唯一事件键 `event_id`，同一任务重试不能重复发送。
5. 改造 `backend/app/api/routes.py`：发布前只允许 `passed → published`，并校验 tenant 和权限。

#### 推荐数据模型

新增 `generation_task_item`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `task_id` | UUID | 生成任务 |
| `item_index` | Integer | 批次内稳定序号，`UNIQUE(task_id,item_index)` |
| `thread_id` | String | LangGraph thread |
| `status` | String | queued/running/stored/awaiting_review/rejected/failed/cancelled |
| `content_id` | UUID nullable | 成功或拒绝时关联内容 |
| `failure_code` | String nullable | 机器可读原因 |
| `failure_reason` | Text nullable | 脱敏后的摘要 |
| `attempts` | Integer | worker 投递/执行次数 |
| `started_at/finished_at` | timestamptz | 生命周期 |
| `tenant_id` | String | 强制非空 |

#### 验收

- 低分耗尽改版时，`ContentItem`、`QualityRecord` 和 item 结果均存在。
- 任意 item 结果都能映射到 `stored/awaiting_review/rejected/failed/cancelled` 之一。
- 一个任务含 2 个成功、1 个拒绝、1 个异常时，任务状态为 `partially_succeeded`，统计数字可从数据库重算。
- 发布 `rejected` 或 `awaiting_review` 内容返回 `CONTENT_STATE_CONFLICT`，数据库状态不变。

### P0-2 租户隔离与 viewer 可见性

#### 目标

把“预留字段”变成真正的访问边界。tenant 不由客户端决定，而由登录用户的认证上下文决定。

#### 改动

1. `User` 增加非空 `tenant_id`；现有单租户数据迁移到 `DEFAULT_TENANT_ID`，系统管理员如需跨租户操作必须走显式 `system_scope`，不以 `NULL` 表示无限权限。
2. `backend/app/security.py`：
   - JWT 增加 `tenant_id`，但每次请求仍以数据库中的当前用户为准，避免角色/租户变更后 token 永久保留旧权限。
   - 新增 `TenantContext` 和 `require_scope()`；禁止业务层读取请求体中的 tenant_id。
3. `backend/app/schemas.py`：从 `GenerateRequest`、`ModelProfileIn`、知识库上传和样本写入请求中移除客户端可控 `tenant_id`；兼容期收到该字段直接返回 422，不静默接受。
4. 新增 `backend/app/repositories/`：
   - `TaskRepository`, `ContentRepository`, `TraceRepository`, `KnowledgeRepository`, `NotificationRepository`, `SampleRepository` 所有查询必须接收 `TenantContext`。
   - `get(id)` 默认生成 `WHERE id=:id AND tenant_id=:tenant_id`，禁止在路由中直接 `db.get()` 读取租户资源。
5. RAG 检索：`backend/app/rag/retriever.py::retrieve()` 强制增加 `KnowledgeChunk.tenant_id == context.tenant_id`。
6. viewer 策略：`viewer` 的内容列表和详情只能返回 `status='published'`；任务、Trace、成本、知识库和样本仍不向 viewer 开放。
7. 通知读取和标记已读增加 `tenant_id` 与当前用户范围；不能用“全表标记已读”。

#### 数据库策略

- 第一阶段使用应用层强制过滤和非空字段。
- 第二阶段在 PostgreSQL 启用 Row Level Security（RLS）作为数据库兜底，连接事务设置 `app.tenant_id`。
- 迁移前先检测 `tenant_id IS NULL` 的数据并生成报告，禁止静默丢弃。

#### 验收

- 租户 A 的 token 即使知道租户 B 的 UUID，也只能得到 404/403，不得得到资源内容。
- viewer 查询只能看到 published 内容；直接调用详情接口不能绕过列表过滤。
- RAG 查询不会返回其他租户的知识分块。
- 所有 Trace、通知、样本和成本聚合都能按 tenant 重算。

### P0-3 Outbox、唯一幂等和死信

#### 目标

消除“数据库有任务、队列没消息”的双写窗口，并把重试、死信和重复投递变成可查询状态。

#### Outbox 模型

新增 `task_outbox`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 事件 ID，同时作为 Celery task_id 候选 |
| `aggregate_type` | String | `generation_task` |
| `aggregate_id` | UUID | 任务 ID |
| `event_type` | String | `generation.requested` |
| `payload` | JSONB | 只放任务 ID 和版本，不放密钥 |
| `status` | String | pending/sending/sent/failed/dead |
| `attempts` | Integer | 发送次数 |
| `next_attempt_at` | timestamptz | 下次重试时间 |
| `last_error` | Text | 脱敏错误摘要 |
| `created_at/sent_at` | timestamptz | 事件生命周期 |
| `tenant_id` | String | 非空 |

#### 写入和发送流程

1. `create_generate_task()` 在一个数据库事务中写入 `GenerationTask(status='pending')` 和 `TaskOutbox(status='pending')`。
2. 事务提交成功后立即由 relay 尝试发送；API 不直接调用 `send_task()`。
3. relay 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 抢占事件，状态改为 `sending`，调用 Celery 时使用稳定 `task_id=outbox.id`。
4. 发送成功将 outbox 改为 `sent`，任务改为 `dispatched`。
5. Redis/Celery 暂时不可用时按指数退避重试；超过 `OUTBOX_MAX_ATTEMPTS` 进入 `dead`，任务改为 `failed`，并产生运维告警。
6. worker 使用 `task_id` 幂等；重复消息只重新读取 item 状态，不重复调用已完成的 LangGraph thread。

#### 去重约束

将现有普通索引替换为 PostgreSQL 部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_generation_task_active_request
ON generation_task (tenant_id, request_hash)
WHERE status IN ('pending', 'dispatched', 'running', 'awaiting_review');
```

API 仍可先查以提供友好错误，但唯一索引是最终并发保证。`request_hash` 的输入必须包含规范化后的模板版本和 tenant，不能只包含客户端参数。

#### 死信处理

- `task_outbox.status='dead'` 是数据库死信；Celery broker 的 rejected task 也必须记录 `task_failure`。
- 增加 `POST /api/ops/outbox/{id}/replay`，只允许 admin，重放前必须显示上次错误和当前状态。
- 重放必须生成新的发送尝试，不得复制任务或绕过幂等索引。

#### 验收

- 模拟 `db.commit()` 成功、Redis 连接失败：任务最终被 relay 重试或进入 dead，不能永久 pending 且无人知晓。
- 100 个并发相同请求最多创建 1 个 active task。
- 同一 Celery task_id 投递两次，只有一套内容和 Trace 结果。
- dead 任务可被管理员审计和安全重放。

### P0-4 生产安全基线与工具权限

#### 配置 fail-fast

改造 `backend/app/config.py`：

- 增加 `ENVIRONMENT=development|test|staging|production`。
- `production` 下拒绝以下值：`JWT_SECRET` 默认值、`SEED_ADMIN_PASSWORD=admin123`、Compose 示例数据库密码、Langfuse 默认 `NEXTAUTH_SECRET/SALT/ENCRYPTION_KEY`。
- 生产启动时校验 `LLM_API_KEY`、`EMBEDDING_API_KEY`、数据库密码和 JWT secret 长度；缺失直接退出，不在运行中才失败。
- `.env.example` 只保留空值或明显占位符，真实密钥仅通过 secret manager 或部署环境注入。

#### 工具调用 allowlist

当前项目虽然主要调用 HTTP 模型接口，但后续 Agent 工具必须经过 `ToolPolicy`：

| 控制 | 规则 |
|---|---|
| 工具注册 | 工具必须有稳定名称、输入/输出 Schema、超时和所需权限 |
| 租户 | 工具调用上下文携带 tenant_id 和 user_id，不允许工具自行选择租户 |
| 网络 | 仅允许配置的域名/HTTP method，默认拒绝任意 URL |
| 数据 | prompt、Trace 和异常日志脱敏；禁止把 API key 写入 JSONB |
| 超时 | 每次调用有连接/读取/总超时，超时归类为可重试或不可重试 |
| 审计 | 记录 tool_name、参数摘要、结果摘要、操作者、trace_id 和权限判定 |

#### 验收

- 生产环境使用默认 JWT secret 或管理员密码时启动失败。
- 未在 allowlist 的工具、域名和权限组合在服务端返回 `PERMISSION_DENIED`。
- 任何工具调用都能通过 trace_id 查到调用者和脱敏参数摘要。

## 6. P1 详细设计

### P1-1 API、Repository 和 Service 拆分

#### 目标

把 `backend/app/api/routes.py` 从上帝模块降为薄接口，不改变外部 URL，先降低修改风险。

#### 目录

```text
backend/app/
├── api/routes.py              # 路由、依赖、响应映射
├── services/
│   ├── generation_service.py  # 创建任务、校验参数、Outbox
│   ├── content_service.py    # 审核、发布、状态迁移
│   ├── quality_service.py    # 自动/人工质检、校准
│   ├── knowledge_service.py  # 上传、索引、检索
│   └── operations_service.py # 成本、Trace、健康状态
├── repositories/
│   ├── task.py
│   ├── content.py
│   ├── trace.py
│   ├── knowledge.py
│   └── notification.py
└── domain/
    ├── status.py
    ├── errors.py
    └── policies.py
```

#### 拆分规则

- route 只负责 HTTP 参数、依赖注入、调用 service 和响应模型。
- service 负责事务边界、状态迁移、幂等和业务错误。
- repository 负责带 tenant scope 的查询和持久化，不返回裸 SQL 给 route。
- workflow 只能调用 service/repository 的有限接口，不能直接依赖 API 模块。
- 不为了“分层”创建只有一行转发的无意义类；每个 service 至少拥有一个事务或业务不变量。

#### 验收

- `routes.py` 降至 400 行以内，聚合查询和写操作迁移到 service。
- 业务单测可以不启动 FastAPI，直接测试状态迁移、租户过滤和 Outbox 事务。
- `api -> workflow` 的反向依赖消失。

### P1-2 模板输入与输出 Schema 真校验

#### 输入

在 `backend/app/services/generation_service.py` 中加载模板 `input_schema`，使用 JSON Schema Draft 2020-12 校验 `params`：

1. 模板不存在或 disabled：`TEMPLATE_NOT_FOUND`。
2. 参数校验失败：返回 `INVALID_TEMPLATE_PARAMS`，错误包含字段路径、关键字和脱敏输入摘要。
3. Schema 版本纳入 `request_hash`，模板升级不会与旧版本任务错误去重。
4. 校验后的参数再传给 workflow，workflow 不重复实现一套不一致的参数规则。

#### 输出

改造 `backend/app/engine/structured_output.py` 的 schema 转换：

- 保留对象 required、additionalProperties、enum、min/max length。
- 数组保留 `items`、`minItems`、`maxItems`，禁止全部降为 `List[Any]`。
- 对无法转换为 Pydantic 的 JSON Schema 关键字，保留第二道 `jsonschema` 校验。
- 不把模型返回的额外字段直接写入 payload，按模板策略选择拒绝或剥离。

#### 验收

- `single_choice` 缺少选项、选项数量错误或字段类型错误在 API 422 阶段返回。
- 模型返回不符合 `minItems/maxItems` 的数组时，重试和最终失败行为可测试。
- 输入校验错误不产生 Celery 任务、不消耗 LLM 调用。

### P1-3 取消、暂停与批量并发

#### 目标

使任务具备用户可控的生命周期，并减少批量任务中单条失败对整体延迟的影响。

#### 设计

1. 新增 `POST /api/tasks/{task_id}/cancel`：
   - `pending/dispatched/running` 可请求取消；`published` 不存在于任务状态。
   - 写入 `cancel_requested_at`，不直接杀死 worker。
   - item worker 在每个节点前检查取消标记；LLM 调用使用总超时，不能无限等待。
2. LangGraph state 增加 `cancel_requested`，在 generate、validate、qc、revise 前做合作式退出。
3. 批量任务拆为稳定的 item job：
   - `generation_task_item` 一条 item 一个 Celery 消息；`task_id=task_item.id`。
   - 使用 Celery group/chord 或数据库聚合，不在一个任务中 `for quantity` 串行执行。
   - 并发上限由配置控制，避免把并发压力直接传给模型供应商。
4. 失败分类：
   - 可重试：Redis/DB 临时错误、HTTP 429、网络超时。
   - 不可重试：Schema 永久错误、权限错误、模板配置错误。
   - 每类错误都有最大重试次数、退避和最终状态。

#### 验收

- 取消请求在下一个安全检查点生效，未完成 item 最终为 cancelled。
- 单个 item 失败不会阻塞同批其他 item；任务聚合状态可重算。
- 相同 item 重投不会重新调用已完成的 thread。

### P1-4 可观测性、健康检查与成本完整性

#### 健康端点

拆分为：

- `GET /api/health/live`：进程仍能响应，不访问外部依赖。
- `GET /api/health/ready`：检查 DB 连接、Alembic 版本、Redis ping、checkpointer backend；任一关键依赖不可用返回 503。
- `GET /api/health/dependencies`：admin/ops 可见的逐项状态、延迟和降级原因，不返回密钥。

PostgresSaver 初始化失败时：

- development/test 可降级 MemorySaver；
- staging/production 默认直接 not-ready，除非显式 `ALLOW_MEMORY_CHECKPOINTER=true`，且必须产生高优先级告警。

#### Trace 扩展

统一 `trace_id/task_id/item_id/tenant_id`：

- LLM chat：模型、prompt 版本、token、成本、延迟、attempt、结构化校验结果。
- embedding：模型、文本数量、维度、token/费用（供应商有返回时）、延迟、失败分类。
- queue：outbox id、投递次数、broker 延迟、死信原因。
- workflow：节点开始/结束、状态迁移、interrupt/resume、取消原因。

Trace 输出默认脱敏：输入/输出只保存配置允许的字段，原始 API key、Authorization、密码、完整用户上传文件不得写入日志或 TraceLog。

#### RAG 维度

- `KnowledgeChunk.embedding` 的维度由迁移配置固定，不允许运行时将 `settings.EMBEDDING_DIM` 与数据库列不一致。
- 更换 embedding 维度必须执行新表/迁移和重建索引，不允许直接改环境变量后启动。
- indexer/retriever 都携带 tenant scope，并在 embedding 失败时返回结构化降级事件而非静默吞掉。

#### 验收

- DB、Redis 或 checkpointer 不可用时 readiness 返回非 200，并在日志中标出依赖名称。
- 一次 RAG 生成可以用 trace_id 查到 embedding 调用和成本。
- Trace 中不会出现 JWT、API key、密码或完整文件内容。

### P1-5 部署、迁移和 Langfuse

1. PostgreSQL 使用明确的初始化策略：分别创建 `english_edit` 和 `langfuse` 数据库，或使用独立 Langfuse PostgreSQL 服务；禁止依赖“连接一个不存在的数据库后自动成功”。
2. Compose 所有服务使用 healthcheck 和 `depends_on: condition: service_healthy`，backend 启动脚本执行迁移后再启动 API，worker 等待 readiness。
3. 迁移必须支持：预检查、备份提示、向前迁移、回滚边界和数据量评估；不能在运行中的 API 请求路径执行大表锁迁移。
4. 增加备份恢复演练脚本：PostgreSQL 逻辑备份、pgvector 表恢复、LangGraph checkpoint 恢复、Outbox 重放验证。
5. Langfuse 定位为可选导出通道，TraceLog 仍是事实源。Langfuse 不可用不得阻断业务，但必须在 readiness/告警中显示 degraded。

## 7. P2 设计项

### P2-1 模型档案和模板引用一致性

- `template_loader` 入库时检查 `run_config.model_profile` 和 `judge_model` 是否存在；不存在直接拒绝加载模板，而不是运行时静默回退。
- seed 补齐 `lite/standard/high` 或把模板统一改为已存在档案；档案名称、供应商、模型名、价目表必须在一次配置校验中通过。
- 模型路由增加 provider health、cooldown、fallback 次数和预算上限，借鉴 LiteLLM 的 `retry_policy`、`max_fallbacks`、`cooldown_time` 语义，但保持本项目 API 简单。

### P2-2 质量闭环的可复现性

- 人工审核记录必须关联 `reviewer=user.id`，不能固定写 `"human"`。
- 质检阈值、权重、prompt 版本和模型版本写入 `QualityRecord` 快照；后续模板变更不能改变历史解释。
- judge agreement 报告按 tenant、模板版本和时间窗口隔离，样本不足时明确输出“样本不足”，不生成伪精确数字。

### P2-3 配置和版本治理

- 模板、prompt、skill、模型档案都具有版本和 hash；任务保存解析后的版本快照。
- 发布前可回放：输入参数、模板版本、prompt 版本、模型、RAG chunk id、质检记录和人工决定必须能由 trace_id 关联。
- 任何配置变更写审计事件，包含操作者、前后差异和生效时间。


## 11. 指标与验收门槛

### 11.1 可靠性指标

| 指标 | 口径 | 目标 |
|---|---|---:|
| 任务投递成功率 | `outbox.sent / outbox.created`，排除 dead | ≥99.9% |
| 永久 pending 任务数 | `pending` 且无活跃 outbox 超过 10 分钟 | 0 |
| 终态可解释率 | 有 item result 且有状态/原因的 item 数 ÷ 完成 item 数 | 100% |
| 重复 LLM 调用率 | 同一 `task_item_id + node + attempt` 的非预期重复调用 | 0 |
| 取消生效率 | 请求取消后 2 个安全检查点内终止的比例 | ≥99% |

### 11.2 安全指标

| 指标 | 目标 |
|---|---:|
| 跨租户读取成功数 | 0 |
| viewer 读取非 published 内容数 | 0 |
| 默认生产密钥启动成功数 | 0 |
| 未授权工具调用成功数 | 0 |
| Trace 敏感信息泄漏事件 | 0 |

### 11.3 可运维指标

- readiness 能在 5 秒内报告 DB、Redis、checkpointer 状态。
- 单个任务从 `trace_id` 能关联到 outbox、item、workflow 节点、LLM/embedding 调用、质检和发布审计。
- 备份恢复演练每月至少一次，RPO ≤24 小时，RTO 目标 ≤60 分钟（个人部署规模下的阶段目标）。
- 失败、死信、跨租户拒绝、默认配置拒绝都必须有结构化日志和告警事件。

## 12. 开源项目可借鉴设计

这些项目只作为设计参照，不代表当前项目已经具备其能力。

| 项目 | 可直接借鉴 | 不应直接照搬 |
|---|---|---|
| LangGraph | `BaseCheckpointSaver` 的 `get/put/put_writes/delete_thread` 契约；节点 RetryPolicy；interrupt/pending writes 测试 | 它不提供业务 RBAC、租户隔离、Outbox 和发布状态约束，不能把 checkpointer 当业务一致性方案 |
| Temporal | Workflow/Activity/Task Queue 分层；append-only event history；ack、DLQ、cancel/terminate/reset、指数退避 | Temporal Server 对当前项目过重，deterministic workflow 和多服务部署成本高 |
| Haystack | `add_component()`/`connect()` 的组件输入输出契约；YAML pipeline 序列化；PipelineSnapshot；trusted-module allowlist | Snapshot 不是完整 durable execution，也不替代消息可靠投递和权限系统 |
| LiteLLM | retry/fallback/cooldown/health check；user/team/key/tool allowlist；统一 OpenAI 错误契约；成本 claim 幂等 | Router/proxy 体量大，不能把其复杂配置和依赖整体引入当前个人项目 |

### 12.1 借鉴落点

1. **LangGraph**：只借鉴 checkpoint 接口和恢复测试，生产降级策略由本项目的 readiness 决定。
2. **Temporal**：借鉴 item job、事件历史、取消和 DLQ 的概念，在 PostgreSQL + Celery 现有栈内实现最小子集。
3. **Haystack**：借鉴 Schema 化组件和 YAML 编排，未来新增数据源/工具时保持输入输出契约稳定。
4. **LiteLLM**：借鉴模型健康、fallback、cooldown 和成本幂等，收敛到 `engine/router.py` 与 `TraceLog`。

## 13. 风险、回滚与决策记录

| 风险 | 处理方式 |
|---|---|
| tenant_id 回填错误造成资源不可见 | 迁移前生成映射报告和备份；先应用层双读校验，再设非空/RLS |
| Outbox relay 重复发送 | 稳定 Celery task_id + item 唯一键 + 状态条件更新，禁止靠内存锁 |
| 状态收紧导致旧客户端无法发布 | 先发布错误码和前置状态校验，前端按状态禁用按钮；不提供绕过参数 |
| PostgresSaver 不可用导致服务不可用 | staging/production readiness 失败；development/test 可显式允许 memory 并标记 degraded |
| item 并发放大供应商限流 | 全局并发上限、模型级 semaphore、429 指数退避和 cooldown |
| RAG 维度迁移期间检索不可用 | 双表/双索引切换，重建完成后再切换 active embedding profile |
| 大范围 routes 拆分引入回归 | 每批保持 URL/响应兼容，先迁移读接口，再迁移写接口，保留契约测试 |

### 13.1 明确不接受的回滚方式

- 不把 `tenant_id` 重新开放给客户端来“临时解决”兼容问题。
- 不在生产环境默认切回 MemorySaver 来掩盖 Postgres 故障。
- 不删除失败/拒绝记录来让任务统计显示成功。
- 不通过管理员权限绕过内容状态迁移。

## 14. 完成定义（Definition of Done）

3.0 只有在以下条件全部满足时，才能把对应 P0/P1 项标记为完成：

1. P0 证据表中的 C-01 至 C-10 均有代码修复、回归测试和迁移记录。
2. API、worker、workflow、repository、数据库事务和 outbox 的边界有模块级测试。
3. `docs/优化记录.md` 为每次代码/迁移改动追加 `OPT-0XX`，写明根因、文件、验证结果和量化对比。
4. `docs/tasks.md` 为对应 J/P 任务更新状态，不使用“已完成”描述未验证的设计目标。
5. CI 通过 lint、单测、真实 PostgreSQL 集成测试和覆盖率门槛。
6. 至少完成一次 worker kill/restart、Redis 故障、跨租户访问、Outbox dead/replay 和数据库恢复演练。
7. 生产 Compose 不含可用默认密钥；readiness 能阻止关键依赖未就绪的实例接收流量。
8. 对外文档和简历只能使用测试和运行数据支持的表述，不把“预留字段”写成“多租户已实现”，不把“可降级”写成“必达”。
