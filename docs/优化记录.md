### OPT-026：交付审查修复 —— 门槛接线、GenState 显式化、温度配置化、lint 全绿

**日期**：2026-09-06
**类型**：修复 + 配置 + 基础设施（外部交付审查驱动的修复批次）
**影响范围**：workflow/graph、engine（温度）、tests、pyproject、.github、全仓格式化

#### 问题 / 动机（外部审查发现）

- **P0-B 覆盖率门槛悬空**：`cov-fail-under` 仅存在于 pyproject 注释，CI integration job 实际命令是裸 `pytest`——覆盖率跌破 80% CI 仍绿，"80% 门槛"是不存在的声明。

- **P0-A 版本控制**：项目本体从未入库（见 tasks.md 里程碑与独立仓库初始化，随本修复批次执行）。

#### 改动

- CI integration job 显式 `pytest --cov-fail-under=80`（门槛接线），并修正 pyproject 注释口径。
- `GenState` 显式声明三个注入键（附原因注释）；测试模板阈值改为 50.0（刻意 ≠ 全局默认 70.0）、灰区分数重标定至 [40,50)、`max_revise=2` 非默认值——键传播从"恰好相同所以盲"变为"可证行为"。
- `LLM_TEMPERATURE=0.7` / `JUDGE_TEMPERATURE=0.3` 入 config；`run_generation_standalone` docstring 说明 thread 口径。
- 新增 CI lint job（black --check / isort --check-only / flake8）；全仓 black 格式化（63 文件中 39 个重排，独立验证 180 测试行为不变）；新增 `.flake8`（E203 为 black 切片风格标准豁免）；顺带清理 flake8 暴露的死代码：graph.py 未用 `user_prompt` 赋值与 `build_system_prompt` 导入、routes.py 未用 `QualityCalibration` 导入与 `passed/rejected` 死变量、calibration.py 歧义变量名 `l`。

#### 验证

- `black --check app tests scripts` / `isort --check-only app tests` / `flake8 app` 全部 CLEAN（lint job 有资格绿）。
- 灰区用例在键传播被破坏时会 loudly 失败（阈值 50 vs 默认 70 的设计性差异）。

### OPT-024：LangGraph interrupt 人工卡点（灰区转人工）—— P1-1

**日期**：2026-09-05
**类型**：后端 + 数据库迁移 + 前端接口
**影响范围**：workflow/graph、api/routes、models/迁移 i8d9e0f1a2b3、notification、worker/tasks

#### 问题 / 动机

- 人工审核完全在图外（API 直改 DB），无 human-in-the-loop；灰区内容（分数接近阈值）要么侥幸入库要么白白熔断（G12）。

#### 设计要点（对设计文档的一处修正）

- 设计文档草稿的 human_review 单节点两段式不可行：interrupt 抛出时同节点内先做的落库副作用不写检查点，恢复后节点重执行会重复落库。实现改为**两节点模式**：`submit_review`（落库 awaiting_review + auto 记录 + 通知，正常返回后状态写入检查点）→ `human_review`（interrupt 前零副作用，恢复后应用裁决）。

#### 改动

- 模板级开关：`run_config.human_review = {enabled, gray_margin}`（默认关闭，零行为变化）；`after_qc` 升级为四路由：达标入库 / 灰区转人工（不消耗改版预算）/ 低分改版 / 达上限熔断。
- `submit_review_node`：条目落库（status=awaiting_review，**thread_id 存入条目**）+ auto 质检记录 + 站内通知（新类型 content_awaiting_review）。
- `human_review_node`：`interrupt({content_id, qc_score, dimension_scores})` 暂停；`Command(resume)` 恢复后写 manual 质检记录、更新条目终态（passed/rejected）、驳回时通知。
- `resume_human_review(thread_id, decision, session)`：review API 凭条目 thread_id 恢复图（依赖 OPT-018 持久化 checkpointer 跨进程恢复）。
- `review_content` API：thread_id 非空且 awaiting_review → 恢复路径；存量条目走旧路径（完全兼容）。
- worker `process_generation_task`：识别 `__interrupt__` 结果计为 awaiting（不计成败），任务汇总 status=partially_succeeded；返回体增加 awaiting 计数。
- 迁移 `i8d9e0f1a2b3`：content_item + thread_id；ContentOut 增 thread_id。

#### 验证

- `tests/test_human_review.py`（13 用例）：灰区中断+落库+通知、恢复通过/驳回（manual 记录/终态/通知断言）、高分直入库、低于灰区走改版、开关关闭保持旧行为（4 次生成后熔断）、after_qc 六条边界路由。
- 全量 pytest 175 passed。

#### 量化对比

| 指标 | 改前 | 改后 |
|------|------|------|
| human-in-the-loop | 图外 API 直改 | LangGraph interrupt + Command(resume)，跨进程恢复 |
| 灰区内容处置 | 二选一（入库/熔断） | 人工裁决，不消耗改版预算 |
| 单测数 | 161 | 175 |

### OPT-023：修复改版链路双生成 Bug（质检反馈从未生效）

**日期**：2026-09-05
**类型**：Bug 修复（实施 P1-1 状态机测试时发现）
**影响范围**：workflow/graph（revise/generate 节点）、prompts/、structured_output

#### 问题 / 动机

- `revise_node` 自行调用一次 `generate_with_fallback`，随后无条件边 `revise->generate` 使 generate 节点**再次**生成：每次改版双倍 LLM 调用（成本 ×2）；且 generate 节点用原始 params 重新生成，revise 节点的改版草稿被无条件覆盖，`revise_context`（质检反馈）从未进入生成 prompt——"携带质检反馈改版"从未真正生效。

#### 改动

- `revise_node` 不再调用生成，只准备上下文：`params.revise_context = {previous_draft, qc_score, dimension_scores}`，计数 +1。
- `generate_node` 检测 revise_context，渲染新 `prompts/revise-instruction.st`（质检总分/维度分/上一稿）并入 `params.revise_instruction`。
- `generate_structured` 消费 `params.revise_instruction` 并入 user prompt——改版请求真正携带上一稿与质检反馈。

#### 验证

- `tests/test_human_review.py` 新增 2 回归用例：revise 节点调用生成即失败（assertion）、generate 节点注入 revise_instruction（含分数/上一稿/关键词）。
- 状态机用例修正后：改版路径 generate 调用次数从 3 次降为 2 次（1 次初始 + 1 次改版），熔断路径从 7 次降为 4 次。
- 全量 pytest 175 passed。

#### 量化对比

| 指标 | 改前 | 改后 |
|------|------|------|
| 每次改版 LLM 调用 | 2 次（1 次被覆盖浪费） | 1 次 |
| 质检反馈进入改版 prompt | 否（形同虚设） | 是（revise-instruction.st 注入） |

### OPT-019：Celery 任务可靠性（acks_late + 瞬态重试 + 僵尸恢复）—— P0-6

**日期**：2026-09-05
**类型**：后端 + 测试
**影响范围**：worker/celery_app、worker/tasks、新增 worker/recovery、config

#### 问题 / 动机

- worker 崩溃后任务永久卡 running（无 acks_late、无重试、无恢复）；"可靠队列"撑不住拷问（G7）。

#### 改动

- `celery_app.conf`：`task_acks_late=True` + `task_reject_on_worker_lost=True`（执行完才 ack，崩溃重投）；`broker_transport_options.visibility_timeout=3600`（须大于硬超时 900s，防提前重投）。
- `process_generation_task`：`bind=True, max_retries=TASK_MAX_RETRIES(3), autoretry_for=(redis ConnectionError/TimeoutError, sqlalchemy OperationalError), retry_backoff=True, default_retry_delay=60, acks_late=True`。仅瞬态基础设施错误重试；业务异常不重试，维持部分成功语义。**重投/重试幂等性由 OPT-018 的 thread 级检查点保证**（两项同批为硬约束）。
- 新增 `app/worker/recovery.py::recover_stale_tasks`：running 且 updated_at 超过 `STALE_TASK_SECONDS(1800)` 的任务重置 pending 并重新入队；`worker_ready` 信号触发，失败仅告警不阻断启动。

#### 验证

- `tests/test_worker_recovery.py`（5 用例）：僵尸任务重置+入队、无僵尸 no-op、cutoff 口径、投递语义（acks_late/reject_on_worker_lost/visibility_timeout）、任务重试语义（max_retries/autoretry_for/acks_late）。
- 全量 pytest 150 passed。

#### 量化对比

| 指标 | 改前 | 改后 |
|------|------|------|
| worker 崩溃后任务 | 永久卡 running | 重投 + 重试 + 启动恢复三重兜底，终态必达 |
| 幂等性 | 无 | thread 级检查点，已完成条目不重复生成 |

### OPT-018：Checkpointer 持久化（MemorySaver → PostgresSaver）—— P0-3

**日期**：2026-09-05
**类型**：后端 + 依赖
**影响范围**：workflow/graph、config、requirements

#### 问题 / 动机

- checkpointer 为进程内 MemorySaver，重启即失，"断点续跑"只有半个（G3，原注释自认"生产环境应替换"）。

#### 改动

- requirements：新增 `langgraph-checkpoint-postgres` + `psycopg[binary]`。
- `graph.py`：`_get_checkpointer()` 惰性单例（双检锁）——默认 `CHECKPOINTER_BACKEND=postgres`，SQLAlchemy 串转 psycopg3 DSN，`autocommit=True, prepare_threshold=0, connect_timeout=5`（快速失败不拖慢启动），`setup()` 幂等建表；初始化失败（包缺失/连不上）告警降级 MemorySaver；`reset_checkpointer()` 供测试隔离。
- `build_graph` 编译时取单例；`run_generation` docstring 补充续跑语义：对已完成 thread 重复 invoke 直接返回落库终态，中断 thread 从最后检查点续跑 —— 任务级重投/恢复因此幂等（配合 OPT-019）。

### OPT-014：质检权重反向校准 — 数据驱动质量闭环（J1）

**日期**：2026-08-13
**类型**：后端 + 前端 + 数据闭环
**影响范围**：质检引擎、工作流、API、前端看板

#### 优化前

- 质检维度权重固定在模板 YAML 中，无法根据实际质检结果动态调整

- J1 质检标准校准因"缺乏校准样本与真实驳回数据"暂缓

#### 优化后

**闭环设计**：低分自动改版 → 人工驳回记录 → 假阳性样本（auto 高分但 manual 驳回）→ 计算每维放水度 → 下调放水维度权重 → 下次质检更准 → 驳回率下降

  - `collect_labeled`：从 DB 收集既有 auto 又有 manual_review 标注的内容对
  - `recalibrate`：编排 collect → fit → 持久化，含守卫（≥20 标注 + ≥5 假阳性）
  - `get_effective_weights`：读取最新校准覆盖权重（无则回退模板默认）
- `quality.py` `_aggregate_score` 支持 `weights_override` 参数：质检聚合时优先使用校准权重
- `graph.py` `qc_node` 接入 `get_effective_weights`：质检时自动读取覆盖权重
- 新增 API：`POST /api/quality/calibrate`（触发校准）+ `GET /api/quality/calibration`（查询记录）
- 前端看板页新增"质检校准中心"：一键校准 + 生效/默认权重对比表 + 驳回率展示
- 8 个校准纯函数单测：放水度计算、降权归一化、下限钳制、覆盖权重聚合

### OPT-008：nginx 反向代理动态解析 backend（消除 502）

**日期**：2026-08-13
**类型**：Bug 修复 + 基础设施
**影响范围**：前端部署（nginx 反向代理）

#### 问题 / 动机
- 前端 `Request failed with status code 502`：nginx `proxy_pass http://backend:8000` 在 worker 启动时解析一次 upstream 并缓存 IP。
- 后端容器重建换 IP 后，frontend 的 nginx 仍连旧 IP（已不存在的容器）→ 所有 `/api/*` 请求 502（静态资源不受影响）。
- 直接 `docker compose up -d frontend` 因配置未变不会重建容器，需 `restart` 才能恢复，问题易复发。

#### 改动
- [frontend/nginx.conf](file:///e:/vibe_coding/english-edit/frontend/nginx.conf#L4)：加 `resolver 127.0.0.11 valid=10s ipv6=off;`（Docker 内嵌 DNS）
- [frontend/nginx.conf](file:///e:/vibe_coding/english-edit/frontend/nginx.conf#L26-L27)：`proxy_pass` 改为变量式 `set $backend http://backend:8000; proxy_pass $backend;`，每次请求经 resolver 动态解析 backend，不再启动时缓存

#### 验证
- 重建 frontend 镜像并重启后，`/api/health`、`/api/dashboard` 经前端代理均返回 200
- frontend 先于 backend 启动完成仍能动态解析成功（无 502）

#### 量化对比

| 指标 | 改动前 | 改动后 |
|------|--------|--------|
| backend 解析时机 | 启动时缓存 IP | 每次请求动态解析 |
| 后端重建换 IP 后 | 502（需手动 restart） | 自动恢复 |

**类型**：Bug 修复
**影响范围**：生成引擎

- [structured_output.py](file:///e:/vibe_coding/english-edit/backend/app/engine/structured_output.py)：`_normalize_flat` 增加 `if not isinstance(data, dict): return data` 防御，非对象结构原样返回交由 Pydantic 校验判错并触发正常重试，而非崩溃。
- [test_structured_output.py](file:///e:/vibe_coding/english-edit/backend/tests/test_structured_output.py)：新增 list 输入回归测试。

#### 验证
- 后端单测 60 通过（新增 1 条回归）。
- 容器端到端：4 题任务成功 3 题，其中第 3 题日志 `attempt=3` 成功——修复前该题会在 attempt=1 直接崩溃，修复后正确走重试。

#### 量化对比

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| list 返回处理 | 崩溃（AttributeError） | 走重试→Pydantic 校验判错 |
