## 第二场：Function Calling 与工具调用稳定性

### Q1. Function Calling 是什么？模型真的执行函数吗？

**参考答案（30 秒）**：
> LLM **不执行任何函数**。开发者用 JSON schema 描述工具（名称、用途、参数），连同对话一起传给模型；模型若判断需要工具，不输出自然语言，而是输出**结构化的 tool_calls**——要调哪个函数、传什么参数；宿主代码解析并执行真实函数，把结果作为 Observation 喂回给模型继续推理。

**四步流程（背）**：定义工具（JSON schema）→ 模型决策输出 tool_calls → 宿主代码执行 → 结果回喂上下文。

**项目锚点**：「我的 `generate_structured` 的 output_schema + Pydantic 二次校验，就是工具参数生成的等价实现——如果接入 tools API，generate 和 judge 可以无缝封装成工具，状态机节点就变成工具调用节点。」

**雷区**：千万别说「模型调用函数」。执行权永远在宿主代码——这是 Function Calling 的第一性原理，答错直接定性。

### Q2. 工具调用怎么做得更稳？（字节原题：工具超时、重试、幂等怎么处理）

**参考答案（40 秒）**：
> 工具调用的可靠性 = **超时 + 重试策略 + 幂等兜底 + 参数双校验 + 错误可读回喂**，五件套。
> ① **超时**：单次调用设 120 秒超时，连接挂起不阻塞整条链路，超时走降级；
> ② **重试**：只对瞬态基础设施错误自动重试（网络抖动、DB 不可用）；业务失败不重试，避免烧钱；
> ③ **幂等**：任务可能被重复投递，靠检查点保证重复执行不产生重复结果；
> ④ **参数校验**：工具入参必须经过代码层校验，不信任模型给的参数——我的做法是 Pydantic 二次校验；
> ⑤ **错误回喂**：校验失败时把字段级错误摘要回注给模型（reask），让它对照修正，而不是原样重发。

**项目锚点**：`STRUCTURED_RETRY_FEEDBACK` + `retry-feedback.st`（错误回喂）、`_get_openai_client` 超时配置、`autoretry_for` 瞬态重试、PostgresSaver 幂等——全都有代码落点，这是你答工具稳定性题的弹药库。

**追问防御**：「错误码怎么返回给模型？」→ 答：错误摘要走 `retry-feedback.st` 模板，结构化列出字段路径/错误类型/错误输入，模型能精确定位改哪里。

### Q3. 你项目里的"结构化输出"和 Function Calling 是什么关系？

**参考答案**：
> 同源。Function Calling 本质上也是"让模型输出结构化 JSON 参数"；我的 output_schema 就是工具参数 schema 的雏形，Pydantic 校验就是工具入参校验。区别只是：Function Calling 由模型**自主决定何时调**，我的流水线是**编排层决定何时生成**——执行权都在代码，模型都只负责产出结构。

## 第三场：多 Agent 协作与记忆

### Q4. 多 Agent 之间互相推诿任务怎么办？

**参考答案（分层防御）**：
> ① **责任边界清晰**：每个 Agent 有明确输入输出、权限和失败兜底——职责模糊是推诿的根源；
> ② **通信协议结构化**：Agent 间消息用固定 JSON schema，参数校验不过直接判失败，不让模型自由发挥；
> ③ **编排者仲裁**：orchestrator 管路由和终局——Agent 超时、连续失败、能力边界外，由编排者接管或降级；
> ④ **预算与轮次上限**：协作轮次设硬顶，防互相踢皮球无限循环（同 max_iterations 思想）。

**项目锚点**：升级方案——题型 Specialist（生成）+ Critic（judge 质检）+ Orchestrator（按分数路由：达标入库/带反馈改版/转人工），改版环就是两个 Agent 的"多轮协作"，max_revise=3 就是协作轮次上限。

### Q5. 复杂任务怎么拆分？为什么要拆？

**参考答案**：
> 拆分的目的是**让每一步可验证、可评估、可恢复**——单次 LLM 调用不可靠，拆成小步骤后每步都能校验，失败只重做该步而不是全盘重来。
> 拆分维度：按子目标（如：先定试卷蓝图再逐题生成）、按阶段（生成→质检→入库）、按数据维度（按题型/知识点分批）。

**项目锚点**：「我批量生成就是按条拆分——每条内容独立 thread_id、独立质检、单条失败不影响整批，这就是任务拆分的粒度收益。」

### Q6. Agent 的记忆机制？

**参考答案**：
> 三层记忆：**短期记忆** = 上下文窗口内的对话历史；**长期记忆** = 外部持久化（向量库/数据库），跨会话可用；**工作记忆** = 当前任务的执行状态（进行到哪一步、中间结果）。
> 生产要点：短期记忆有窗口上限要截断/摘要；长期记忆用 embedding 检索而非全文塞入；工作记忆必须持久化，否则进程一崩任务就丢。

**项目锚点（全是你的）**：工作记忆 = LangGraph state + PostgresSaver（任务状态持久化）；长期记忆 = pgvector 知识库 + 样本池；TraceLog = 经验回放（每次调用的输入输出都可追溯）。

## 第四场：系统设计与 RAG 深问

### Q7. 设计一个能上线的 Agent 系统，你怎么拆？（字节/阿里都爱考，送分框架）

**参考答案（六部分框架，背）**：
> ① **任务入口**：理解用户目标、补齐缺失参数、识别任务风险（输入 schema 校验）；
> ② **规划与状态管理**：把复杂任务拆成可验证的小步骤，状态全程持久化，支持断点续跑；
> ③ **工具执行层**：可靠执行——超时、重试、幂等、参数双校验（就是工具稳定性五件套）；
> ④ **评估与反馈**：自评（LLM-as-Judge）+ 人工介入（HITL）+ 失败反馈回流；
> ⑤ **可观测性**：全链路 trace、成本、延迟、成功率，单次任务可回放；
> ⑥ **安全与治理**：权限控制、内容审核、成本上限、熔断。

**项目锚点**：①②③⑤你**全部已实现**（API+schema / 状态机+checkpointer / engine 可靠层 / TraceLog），④⑥已实现大半（judge+interrupt / JWT 权限）。答题时直接说「我项目就是按这个框架落地的，逐条对照」，这是全场最强的回答之一。

### Q8. RAG 检索质量差怎么办？（字节追问：RAG 链路每个环节都能优化幻觉）

**参考答案（逐环节，背）**：
> ① **分块策略**：按语义边界切块、设置合理块大小与重叠，避免切碎语义或混入噪声；
> ② **Embedding 选型**：模型与维度要匹配场景（维度高信息多但成本高，维度低更省）；
> ③ **检索策略**：多路召回（向量 + 关键词混合）、查询改写（把用户问题改写得更适合检索）；
> ④ **重排（rerank）**：召回 Top-K 后用重排模型精排，提升相关性——这是检索质量差的常规解法；
> ⑤ **生成端约束**：只依据检索内容作答、要求引用溯源、检索为空时明确说不知道（防幻觉）。

**项目锚点**：你的 RAG 是「按知识点查询 pgvector → 命中注入 prompt」，答完通用链路后补一句「我目前的检索策略是单路向量 + 知识点直查，rerank 和混合检索是我列出的增强方向」——诚实 + 有方向。

### Q9. embedding 向量维度怎么选？

**参考答案**：维度 = 信息密度与成本/延迟的权衡。高维度区分度好但存储和计算贵，低维度省但可能损失语义。工程上先按模型默认（如 text-embedding-v3 默认 1024 维），用评测数据对比不同维度下的检索命中率再定，不拍脑袋。

## 第五场：评估与通用题

### Q10. LLM-as-Judge 有哪些坑？（你有最全答案）

**参考答案**：
> 四个经典偏置：**位置偏置**（长答案、靠前的答案容易高分）、**自偏好**（judge 与生成同模型时袒护自己）、**尺度漂移**（同一尺度不同轮次打分不一致）、**prompt 敏感**（评分标准表述一变分数就变）。
> 解法对应：rubric 结构化注入（钉死评分尺度）、独立 judge 模型链（防自偏好）、多轮采样均值（降抖动）、kappa 与人工对齐（校正）+ 假阳性反向校准（数据驱动修正）。

**项目锚点**：你四件全有（quality.py / resolve_judge_model / aggregate_rounds / agreement.py / calibration.py）——这是你答"评估体系"时的王牌，答完直接说「这四类偏置我在项目里分别用 X/Y/Z 治理」。

### Q11. 你遇到的最大 Bug？（STAR，必背）

用 OPT-023：测试驱动暴露改版链路双生成——每次改版 2 次 LLM 调用且质检反馈从未真正进入生成 prompt；修复后 2→1 次、熔断路径 7→4 次、反馈真实注入。**要点：bug 靠测试抓出而非读代码，体现测试驱动的工程素养。**

### Q12. 为什么投 Agent 应用开发？

**参考答案（叙事线）**：
> 实习用 Dify 做英语习题生成，摸到低代码工作流的天花板（质量不可控、扩展硬编码、不可观测）→ 自研 LangGraph 编排系统，把生成、评估、人工介入、可观测做成闭环 → 过程中意识到这套骨架就是 Agent 系统的五件套 → 想继续做多 Agent 协作、工具调用、可靠执行这些真正 Agent 化的部分。

**雷区**：别说「因为 Agent 火」。你的故事线有完整动机链，这就是答案。

### Q13. LLM 应用成本怎么控制？

**参考答案**：分模型价目表精确核算（prompt/completion 分开计价）→ 降级链选便宜模型兜底 → 重试预算硬顶（max_retry/max_revise）→ 灰区优先人工（不烧改版预算）→ 成本报表按题型/模型/阶段下钻，找到成本大头针对性优化。
