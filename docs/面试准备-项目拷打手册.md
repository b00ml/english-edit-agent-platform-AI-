### ⚠️ 简历表述偏强 / 需补口径的 5 处（面试深挖必露馅）

1. **「真 Postgres 集成测试级验证」跨进程恢复 —— 表述过强**
   事实：CI integration job 显式设 `CHECKPOINTER_BACKEND: memory`（backend-ci.yml 注释原文：「interrupt 恢复在同进程内验证（PostgresSaver 降级逻辑由单测覆盖）」）。也就是说：
   - 5 个端到端测试用的是**真 Postgres 数据库 + memory checkpointer**；
   - **PostgresSaver 上的跨进程 Command(resume) 从未在 CI 端到端验证过**，只有 test_checkpointer.py 的 4 个单测。
   面试答法：诚实承认验证分层——「跨进程恢复的正确性依赖 PostgresSaver 的持久化语义（已单测覆盖），端到端 interrupt/resume 全流程用真 Postgres DB + 进程内 Celery 验证；完整『双进程真 Postgres』端到端是我列出的已知缺口，下一步补」。**主动暴露缺口 + 给修复方案，比被问出来强 10 倍。**

2. **「多轮均值降抖动」—— 默认配置是 1 轮**
   `JUDGE_SAMPLE_ROUNDS: int = 1`（config.py 注释：「rubric 已使单次稳定，默认 1，需降噪时调高」）。README 的「多轮均值降抖动」是能力，不是默认行为。别被问「你默认几轮采样」时卡壳。

3. **灰区转人工「默认关闭」**
   `after_qc` 里 `human_review_config.enabled` 为 False 时灰区分支不生效。集成测试里也是现造一个 `single_choice_hr` 模板（run_config 里打开开关）才测的。面试若被问「线上灰区转人工是默认开的吗」——答：模板级配置开关，按题型启用，避免所有题型都堆到人工。

4. **「治理自偏好偏差」—— 是配置链，不是强制**
   judge 模型解析链兜底到 `LLM_MODEL_NAME`。如果没配 `JUDGE_MODEL_NAME`、模板也没配 `judge_model`，judge 和生成是**同一个模型**，「自偏好治理」就落空了。简历应改成「提供独立 judge 模型配置链，支持 judge 与生成模型异族，降低自偏好偏差」。

5. **kappa「≥30 样本守卫」—— 30 在报告脚本里，不在自动校准里**
   - `scripts/judge_agreement.py`：n<30 提示「样本不足，不建议作为验收数字」（报告门槛）；
   - `calibration.py` 自动校准守卫是 **20 条标注 + 5 个假阳性**（`_MIN_LABELED_SAMPLES=20, _MIN_FALSE_PASS=5`）。
   简历写「≥30 样本守卫」会被追问具体层。准确说法：一致性报告门槛 n≥30；自动校准触发守卫 20+5。

## 1. 拷打模块 A：项目动机与选型（几乎必问，开场 5 分钟）

**Q1. 你之前用 Dify 做英语习题生成，为什么要推翻重写？**
- 回答骨架（三层理由，对应你简历的三个痛点）：
  1. **无质量闭环**：Dify 工作流是「生成即交付」，没有自动质检、没有人工反馈回流，内容质量不可控；
  2. **题型扩展硬编码**：每加一种题型要改工作流/代码，无法配置化接入；
  3. **可观测性缺失**：看不到单条成本、模型调用链路、失败归因，无法核算和优化。
- 追问防御：「Dify 也有监控和插件机制，为什么不够？」→ 我们要的是**代码级状态机控制**（人工卡点 interrupt、断点续跑、幂等重投）、**结构化输出的服务端二次校验**、**成本分账埋点**，这些在低代码工作流里做不深。

**Q2. 为什么选 LangGraph，而不是自己写一个 pipeline / 用现成 Agent 框架？**
- 关键论点：**断点续跑 + 人工中断 + 状态持久化是这个项目最难的三件事**，自写状态机极易出错——我自己的 OPT-023 就是证据：改版链路双生成、质检反馈从未生效，正是图逻辑 bug，靠手写很难发现。
- LangGraph 提供：checkpointer（PostgresSaver）、interrupt/Command（HITL 一等公民）、条件边（状态机语义）。
- 追问防御：「为什么不用 LangGraph 的 ReAct/Agent 预设？」→ 生成流水线不是「思考-行动循环」，是**确定拓扑的多阶段质量门**，StateGraph 精确表达；Agent 预设反而引入不需要的规划自由度。

**Q3. 「AI 原生内容生产线」的「生产线」指什么？瓶颈在哪？**
- 答：把单次 LLM 调用封装成**可评估、可重试、可回放**的工序，串成 选题→生成→校验→质检→改版→入库→发布，类比工厂产线：每个工位有质检门（gate），不合格回流返工（改版环），超出返工次数报废（reject）。
- 瓶颈诚实版：目前瓶颈在**人工终审**（质量闭环的地面真值来源）和**改版环的 LLM 成本**；单条成本可核算（TraceLog），所以能算清「改版几次最划算」。

## 2. 拷打模块 B：LangGraph 状态机（核心区，必深挖）

**Q4. 默画你的八节点图，逐个节点说输入/输出。**（必背）
```
START → generate（RAG注入 + 主→备→默认降级 + 改版反馈注入）
      → validate（required 字段兜底）→ 失败回 generate
      → qc（LLM-as-Judge 逐维度打分加权；校准权重覆盖）
        ├─ score ≥ 70           → store（落库 + 绑定 auto 质检记录）→ END
        ├─ 灰区 [70-10, 70) 且开关开 → submit_review（落库 awaiting_review + 写检查点）
        │                          → human_review（interrupt 暂停，等人工）→ END
        ├─ score < 70 且 revise_count < 3 → revise（只准备上下文，不调用 LLM）
        │                          → generate（反馈真实注入）
        └─ score < 70 且达上限     → reject → END
```

**Q5. after_qc 里为什么灰区优先于改版？**
- 灰区（阈值下方 margin 内）内容**接近达标**，再改版收益低、成本高；直接交人工裁决更划算，且**不消耗改版预算**。
- 防御追问：「为什么不把灰区也自动改版一次？」→ 数据上是「边际收益 vs 边际成本」的工程取舍，模板级开关可按题型调。

**Q6. interrupt 的原理？为什么 submit_review 和 human_review 必须拆两个节点？**
- interrupt 的本质：图执行到该节点**暂停并返回**，状态（含已完成节点副作用）已持久化到检查点；恢复时 interrupt() 直接返回人工裁决值继续执行。
- 拆节点的原因（这是你代码注释里的核心设计，要讲出彩）：**interrupt 之前的所有副作用在恢复时不会重放**，但如果把「落库」写在 interrupt 之后，一旦恢复流程异常，条目可能没落库或重复落库。所以 submit_review 先把条目落库 + 写质检记录 + 写检查点，再进 human_review 的 interrupt——副作用与暂停点分离，恢复幂等。
- 追问：「interrupt 抛出的 payload 是什么？」→ `{content_id, qc_score, dimension_scores}`，人工在审查台能看到评分依据。

**Q7. Command(resume) 跨进程恢复依赖什么？checkpointer 挂了会怎样？**
- 依赖 PostgresSaver：检查点存 Postgres，任何进程凭 thread_id 可恢复；worker 挂了重启后，通过 review API 也能跨进程 resume。
- 降级：PostgresSaver 初始化失败自动降级 MemorySaver（可用性优先），但降级后**断点只在进程内**，跨进程恢复失效——这是明确的权衡，面试要主动说。
- **⚠️ 自曝点（必答好）**：「你的 CI 端到端测试用的是 memory checkpointer，跨进程恢复验证过吗？」→ 见摸底结论风险 1 的答法。

**Q8. 幂等：任务重投为什么不会重复生成？**
- thread_id = `task_id:idx` 粒度。已完成 thread：PostgresSaver 直接返回最终 state，**不再执行任何节点**（store 不会重放），所以不重复入库；中断 thread：从最后检查点续跑。
- 追问：「任务部分成功、部分失败后重投，失败的条目怎么处理？」→ 失败条目所在 thread 从检查点续跑（若 generate 已完成则不会重新生成）；配合 Celery 只对瞬态错误自动重试，业务失败不重试、保持部分成功语义。
- 追问：「同一个 thread 并发 invoke 会怎样？」→ LangGraph 层面会争用检查点，所以并发粒度设计在 thread 之间（每任务 quantity 条用不同 idx），单任务内串行。

**Q9. 状态里为什么显式声明 max_revise / quality_threshold / human_review_config？**（展示你踩过坑）
- OPT-026 的 P1 修复：LangGraph 1.2.x 对未声明键宽松传播是未定义行为，升级收紧 schema 会让灰区卡点和模板阈值**静默失效且测试全绿**。显式声明后升级安全。
- 这句话面试官一听就知道你不是调包侠。

## 3. 拷打模块 C：结构化输出（岗位核心能力，必问）

**Q10. 为什么不用 Outlines 约束解码？**
- 云端 API（DeepSeek/Qwen/GLM）**不开放 logits**，无法注入 FSM/正则采样器（需要本地 vLLM/llama.cpp 推理端点才能用）。
- 所以迁移为等效方案：`response_format=json_object` 强制 JSON + **Pydantic v2 动态模型二次校验**（从 output_schema 动态 `create_model`，含 Literal 枚举约束、嵌套递归）。
- 追问：「等效在哪、不等效在哪？」→ 结构合法性等效（字段/类型/枚举）；**不等效的是语义约束**（如「答案必须存在于选项中」这种跨字段关系），语义靠下游 judge 兜底——这个边界必须自己主动说，不然被问住。

**Q11. 重试机制怎么设计？为什么有效？**
- 多轮消息：重试时**回注上次原始输出（assistant 消息）+ 字段级错误摘要（retry-feedback.st）**，模型对照修正，不是原样重发（Instructor reask 等效）。
- 错误摘要：ValidationError 逐条取字段路径/错误类型/输入值（截断 10 条），JSONDecodeError/KeyError 单独说明。
- 追问：「重试 3 次都失败？」→ 抛 StructuredOutputError → 单条失败计入任务 failed，不中断批量（部分成功语义）。
- 追问：「失败尝试的成本记录了吗？」→ 每次调用（含失败）都写 TraceLog，attempt/success 字段区分，所以**重试成本可核算、首过率可统计**（/api/traces/structured-stats）。

**Q12. 模型偶发「嵌套包装」怎么处理？**（细节加分项）
- `_normalize_flat`：顶层缺必填字段但恰有子对象/数组含全部必填字段时，展平取用，避免无谓重试。
- 追问：「这是不是模糊校验、放水？」→ 只处理**结构包装**（模型多包一层），字段完整性仍由 Pydantic 强制，语义由 judge 把关。

## 4. 拷打模块 D：质量闭环（最能体现工程思维的部分）

**Q13. LLM-as-Judge 怎么防止「自己给自己打高分」？**
- 独立 judge 模型解析链：模板 run_config.judge_model > JUDGE_MODEL_NAME > LLM_MODEL_NAME；建议 judge 与生成模型**不同家族**（降低同源偏差）。
- **诚实边界**：这是「配置级治理」——没配 judge_model 时兜底回落同一模型。别吹成「已治理」，说「提供治理能力，生产配置为异族模型」。
- 加分：judge 用低温度（0.3）、rubric 结构化注入（分档评分标准进 user prompt，防尺度漂移）、可选多轮采样均值（JUDGE_SAMPLE_ROUNDS）。

**Q14. Cohen's kappa 为什么是二值判定？为什么不做维度级？**
- 诚实边界（agreement.py 注释原文口径）：**人工标注只记录总分二值**（manual_score>0 通过 / =0 驳回），没有维度级人工标注，所以不能做维度级加权 kappa；报告明确标注这是「二值判定级」一致性。
- 追问：「kappa 实际值多少？」→ 项目处于数据积累期，样本不足时脚本提示 n<30 不作为验收数字。**不要编数字**，回答「机制就绪、数据待积累，报告门槛 n≥30」。

**Q15. 校准闭环的完整链路？**（背下来，这是你简历最高光的点）
```
人工抽检驳回（FP：auto 高分但 manual 驳回）
→ collect_labeled 收集 FP 集与通过集的维度分
→ fit_weights：放水度 lenient_i = mean(FP 维度分) − mean(Pass 维度分)
   （>0 说明该维度对差样本放水）→ 按 α=1.0 降权 → 归一化 + 下限钳制(5%)
→ 阈值再校准：驳回率 > 5% 时收紧到通过集 auto 分 P10
→ get_effective_weights 覆盖 qc 节点权重 → 下次质检更准
```
- 守卫：≥20 标注且 ≥5 FP 才生效（防小样本过拟合），不足时写记录但保持默认权重。
- 追问：「校准在真实数据上跑出效果了吗？降权前后对比？」→ 诚实：机制与测试就绪，真实业务数据未积累到守卫阈值；这正是把「数据回流」做成系统的一部分的原因（样本池 JSONL 可导出微调）。

**Q16. 你的质量闭环里，人工是「必要之恶」还是「核心资产」？**
- 答：人工终审是**地面真值来源**，驱动 kappa 评估 + 校准 + 样本回流三个环节；系统设计目标不是消灭人工，而是**把人工用在刀刃上**（灰区 + 抽检），自动通过率稳定、驳回率 ≤5%（P2 目标）。

## 5. 拷打模块 E：可靠性工程（中间件/系统设计考察）

**Q17. acks_late 的代价是什么？**
- 代价：消息可能**重复消费**（worker 崩溃时任务已执行但未 ack）。必须配合**消费幂等**——你的幂等正是 PostgresSaver thread 级检查点（已完成条目不重复生成）。「acks_late 换至少一次语义，幂等兜底去重」是一句完整的答案。

**Q18. 什么算「瞬态」？业务失败为什么不重试？**
- autoretry_for 只列基础设施错误：Redis 连接/超时、DB OperationalError（网络抖动、重启窗口）；
- 业务失败（生成耗尽、质检失败）重试无意义且烧钱，保持「部分成功聚合」语义（succeeded/failed/awaiting 三态汇总）。

**Q19. 僵尸任务怎么恢复？**
- `STALE_TASK_SECONDS=1800`：running 超时的任务视为僵尸，worker 启动时扫描重置为 pending 重新入队（recovery.py）。
- 追问：「为什么只在启动时扫？」→ 简化一致性（避免多 worker 并发抢重置），成本低。

**Q20. 批量 1000 条的性能瓶颈？并发怎么控制？**
- 现状：单任务内**串行** for 循环（每条第 1 次 LLM 调用 + judge 调用），并发靠 worker `--concurrency=5`（任务间并行）。
- 改进方向（主动说）：① 任务内按 batch 并行（注意同一 PostgresSaver thread 不能并发，需独立 thread_id）；② 生成与质检流水线化；③ 每批独立 Celery 子任务。面试官要的是你知道瓶颈在哪。

**Q21. 成本是估算还是实账？**
- 估算：COST_PER_1K_TOKENS 全局单价 + MODEL_PRICES 分模型价目表，按 usage token 折算。不是云厂商账单。用途是**相对比较与优化决策**（哪个模型/改版几次划算），口径在 README 已声明。

## 6. 拷打模块 F：Agent 岗位视角（最重要！把这个项目「翻译」成 agent 系统）

**Q22. 这个项目看起来是流水线，跟 Agent 应用开发有什么关系？**
这是你简历投 agent 岗必须回答好的问题。翻译框架：
| 你的项目 | Agent 系统对应物 |
|---|---|
| LangGraph 状态机 | Agent 编排运行时（节点=动作，边=策略路由） |
| generate 节点（LLM 调用封装：降级/重试/结构化输出/埋点） | **Agent 的可靠工具执行层** |
| interrupt 人工卡点 | **Human-in-the-loop（HITL）**，Agent 应用标配 |
| PostgresSaver 断点续跑 | **持久记忆/会话恢复**（跨进程、跨重启） |
| TraceLog 全链路埋点 | **Agent 可观测性**（成本/延迟/成功率的单次回放） |
| LLM-as-Judge 质检 + 校准 | **Critic/Evaluator Agent + 自反馈闭环** |
| 改版环（生成↔反馈） | 生成器-评判器多轮迭代（Agent 反思模式） |

结论句：「它本质上是一个**单 Agent 长链路任务执行器**：编排、HITL、记忆、可观测、自评估五件套都在，缺的是多 Agent 协作与工具调用——而这两块正是我下一步想做的。」

**Q23. 如果把它升级成多 Agent 系统，你怎么设计？**（开放题，展示架构视野）
- 方案：Orchestrator（选题/派单/路由）→ 题型 Specialist Agent（生成，继承结构化输出与降级）→ Critic Agent（judge，独立模型）→ 仲裁器（按分数决定终审/返工/入库，对应 after_qc）；改版环升级为 Specialist 与 Critic 的多轮辩论（带预算上限，对应 max_revise）。
- 协作协议：全部走结构化 JSON 消息（你的 output_schema 就是 tool/agent 消息 schema 的雏形）；状态与记忆复用 PostgresSaver + pgvector（RAG 已有）。
- 防追问：「多 agent 的额外成本怎么控制？」→ 预算路由：简单题型单 agent 直出，疑难/灰区才拉起多 agent 辩论。

**Q24. Function calling / Tool use 用过吗？和结构化输出什么关系？**
- 诚实：项目未用 tools API，但 `generate_structured` 的 output_schema + Pydantic 校验就是 function calling 中**工具参数生成**的等价实现；若模型支持 tools API，generate/judge 可以无缝封装成 tool，状态机节点变成工具调用节点。
- 加分：讲你对「结构化输出是 agent 系统地基」的理解——工具调用、任务交接、HITL 决策全部依赖稳定 schema。

**Q25. 假设线上生成质量突然下降，你的排查路径？**（可观测性考题）
- ① trace_id 回放该条：看输入 params、prompt 版本、模型、attempt/success、各次错误摘要；② 看成本/延迟变化（模型侧降级？）；③ 看 judge 各维度分（哪个维度放水）；④ 看校准权重是否被污染（假阳性暴增？）→ 定位到 prompt 版本 or 模型路由 or judge 配置。

## 8. 三个必背 STAR 故事

### 故事 1（最有力）：改版链路双生成 Bug（OPT-023）
- **S**：改版流程成本高（每次改版 2 次 LLM 调用）且改版质量上不去——改版好像「没效果」。
- **T**：写状态机测试覆盖改版路径，断言每次改版只应有 1 次生成调用。
- **A**：测试暴露真相：revise 节点自己生成一次、又被无条件边 revise→generate 再生成一次，第一次结果被覆盖；且质检反馈从未进入生成 prompt（改版形同虚设）。修复：revise 只准备上下文（previous_draft + qc_score + dimension_scores），生成统一收敛到 generate 节点，新 prompt `revise-instruction.st` 注入反馈；加回归断言。
- **R**：改版 2→1 次 LLM；熔断路径 7→4 次；质检反馈真正生效。
- **讲法要点**：「这个 bug 靠读代码很难发现，是**测试驱动的状态机审计**抓出来的」——面试官最想听这句。

### 故事 2：结构化输出稳定化
- **S**：模型输出不稳定，流水线失败率高、成本不可控。
- **T**：云端 API 不开放 logits，Outlines 约束解码不可用。
- **A**：output_schema 动态构造 Pydantic 模型 + json_object 强制 + 错误摘要回注重试（reask 等效）+ 嵌套包装兜底展平 + attempt/success 全量埋点。
- **R**：首过率/重试成本可查证（structured-stats），失败可归因；本地 vLLM 接入时可无缝换约束解码。

### 故事 3：质量闭环从 0 到 1
- **S**：无质量评估、人工驳回率不可控，内容「生成即交付」。
- **T**：建立可评估、可自优化的质检体系。
- **A**：LLM-as-Judge（独立模型链 + rubric 注入）+ kappa 一致性报告（二值口径、n≥30 门槛）+ 人工驳回驱动权重反向校准（假阳性逐维降权 + 阈值再校准）+ 样本池回流。
- **R**：驳回率 ≤5% 的 P2 目标有了机制闭环；校准、评估、回流三条数据链路打通。

## 10. 快问快答（30 秒版本，练到脱口而出）

- **为什么不用 Dify？** 无质量闭环、题型硬编码、不可观测；需要代码级状态机（interrupt/断点/幂等）。
- **八节点？** generate/validate/qc/revise/store/reject/submit_review/human_review。
- **质检怎么打分？** LLM-as-Judge 按模板 quality_rules 逐维度 0-100 + 加权汇总，rubric 进 prompt，校准权重可覆盖。
- **怎么防 judge 自嗨？** 独立 judge 模型配置链 + 低温度 + kappa 人工一致性 + 假阳性降权。
- **结构化输出？** json_object + Pydantic 动态模型二次校验 + 错误摘要回注重试（reask 等效），语义靠 judge。
- **断点续跑？** PostgresSaver，thread_id=task:idx，已完成直接返回终态，重投幂等。
- **人工卡点？** interrupt 暂停图，review API 用 Command(resume) 恢复，跨进程凭 thread_id。
- **最自豪的 Bug？** OPT-023 双生成：测试暴露、2→1 次调用、反馈真正注入。
- **agent 视角？** 单 Agent 长链路执行器：编排/HITL/记忆/可观测/自评估五件套齐全，缺多 Agent 协作与工具调用。
- **最想补的缺口？** 双进程真 Postgres 的跨进程恢复端到端用例；多 Agent 协作层。
